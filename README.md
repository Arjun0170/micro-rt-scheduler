# Micro-RT Scheduler: simulated bare-metal firmware in C

A small, deterministic foreground scheduler and fixed-point PI controller. The
repository is software-only: the timer interrupt, plant, and fault events are
generated by a host simulator. It needs no board, vendor SDK, or communications
interface.

## What it demonstrates

- A 1 ms virtual timer ISR and wrap-safe 32-bit tick comparisons.
- Fixed-priority periodic dispatch with phases, deadlines, release accounting,
  and bounded foreground work (one callback per dispatch).
- A single-producer/single-consumer ISR event ring that drops newest on overflow.
- Q8 fixed-point PI control with output saturation, conditional anti-windup,
  and a latched fault that forces output to zero.
- No heap allocation or platform-specific runtime in the firmware library.

This is a cooperative scheduler, not a preemptive RTOS. All callbacks must be
short and must return. A task that blocks can delay every lower-priority task.

## Run

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
./build/scheduler_sim
```

The simulator targets 50 C, injects a fault at 18 s, clears it at 22 s, and
prints temperature, output duty, and fault state. It also prints task runs and
deadline misses. The plant is intentionally simple; the point is to make task
timing and state changes observable, not to model a physical heater accurately.

## Porting boundary

On a Cortex-M target, a hardware timer ISR would call `sched_tick_isr`, and a
foreground loop would call `sched_dispatch_one`. An ISR could post events with
`sched_post_event_isr`; tasks consume them with `sched_take_event`. The ring
assumes one producer ISR and one foreground consumer. The 8-bit head/tail
indices are atomic on typical MCUs; aligned 32-bit tick access is assumed
atomic on Cortex-M. Other targets need an atomic snapshot or short critical
section. This repository has not been run on physical hardware or measured for
worst-case execution time.

## Scope and limitations

Deadlines are accounted for in simulated milliseconds. Host execution time is
not a real-time guarantee. The controller uses a toy plant, and its gains are
for the simulation only. A real control system would require sensor validation,
actuator limits, timing analysis, and hardware safety review.
